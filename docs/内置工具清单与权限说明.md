# personal-agent 内置工具清单与使用权限说明

> 依据代码整理（`packages/tool`、`packages/core`、`packages/mcp`、`apps/web`、`apps/cli`）。
> 工具执行完整链路：参数校验 → 沙箱检查 → 权限判断 → 执行 → 结果后处理。

## 二、工具属性说明

每个工具继承 `BaseTool`，声明三个权限相关属性（`packages/tool/src/types.ts`）：

- **`requiresPermission`**（默认 `false`）：执行前是否需要权限判断。标记为 `true` 的工具在 `ask` 模式下会触发用户确认。
- **`isDangerous`**（默认 `false`）：是否属于危险工具。当前仅 `bash` 为 `true`；`approval` 模式下所有工具都会要求显式审批。
- **`canBeUsedInSubAgent`**（默认 `true`）：是否允许子 Agent（CLI sub-agent）调用。`ask_user` 因无交互界面而禁用；MCP 工具默认禁用。

### 各类别工具的默认策略

| 类别 | 工具 | 默认执行策略 |
|------|------|--------------|
| file | `read_file` / `list_directory` / `glob` / `grep` | **只读，无需权限**，直接执行 |
| file | `write_file` / `edit_file` | 需要权限（ask 模式下询问用户） |
| shell | `bash` | 需要权限 + 危险标记（ask / approval 模式下均询问） |
| web | `web_fetch` / `web_search` | 需要权限 |
| utility | `todo_write` / `ask_user` | 无需权限 |
| memory | `read_memory` | 无需权限 |
| memory | `write_memory` | 需要权限 |
| plan | `submit_plan` / `get_plan` / `update_plan_step` | 无需权限；`submit_plan` 仅 Plan 模式可用 |

## 三、权限体系（Permission Manager）

### 1. 权限决策结果（三态）

`PermissionManager.check()` 返回三种决策：

| 决策 | 含义 |
|------|------|
| `allow` | 直接放行，不询问 |
| `ask` | 询问用户；仅当工具 `requiresPermission` 或 `isDangerous` 时才真正弹窗 |
| `approval` | 每次执行都要求用户显式审批 |

默认决策为 `ask`（无匹配规则时）。任务/项目特定规则（`target: task:<id>` / `target: project:<id>`）**优先于**全局基线规则（`target: all` 或缺省）。

### 2. 规则匹配

- 规则字段：`tool`（支持 `*` 通配及 `prefix*` 前缀匹配）、可选 `pattern`（正则匹配参数 `path` / `command`）、`action`、`scope`（session / project / global）、`target`。
- 示例：`{tool: bash, pattern: "rm -rf *", action: approval, scope: project}`。

### 3. Web Runtime 的权限模式（每任务独立）

| 模式 | 行为（`runtime.ts requestToolPermission`） |
|------|--------------------------------------------|
| `allow` | 所有工具直接放行 |
| `ask`（默认） | 仅 `requiresPermission` / `isDangerous` 的工具询问用户；会话内可选择"记住本次选择" |
| `approval` | 每个工具执行前都弹出审批 |

CLI 侧对应 Slash 命令：`/allow <tool>`（会话内放行）、`/approval <tool>`（会话内每次审批）、`/permissions`（查看规则）；启动参数 `-y / --yes` 自动批准全部工具（仅限可信工作区）。

### 4. 配置文件权限规则

`tools.permissions` 支持 YAML 配置（Web Runtime 加载）：

```yaml
tools:
  permissions:
    - tool: bash
      action: approval   # allow | ask | approval
      scope: project     # session | project | global
    # 可选 pattern、target: all | task:<id> | project:<id>
```

### 5. MCP 工具权限

- MCP 工具（`mcp__*`）默认 `requiresPermission = true` 且 `isDangerous = true`，即**默认每次需审批**。
- 服务器配置 `autoApprove` 列表中的工具自动放行（支持 `*` 放行全部），并生成对应 `allow` 规则。

```yaml
mcp:
  servers:
    - name: local-tools
      transport: stdio
      command: node
      args: [/path/to/mcp-server.js]
      autoApprove:
        - safe_read_tool
```

## 四、沙箱（Sandbox）

| 约束 | 默认值 | 说明 |
|------|--------|------|
| `restrictPaths` | `true` | 文件工具只能访问当前工作区及 `allowedPaths` 内的路径 |
| `allowedPaths` | `[]` | 额外允许访问的路径 |
| `deniedPaths` | `[]` | 禁止访问的路径（优先于 allow 判断） |
| `deniedCommands` | `rm -rf /`、`format`、`shutdown`、`reboot`、fork 炸弹 `:(){ :|:& };:` | 命中断言即拒绝执行的命令片段（配置可追加） |
| `maxFileSize` | 10 MB | 单次读取文件大小上限 |
| `shellTimeout` | 120000 ms | Shell 命令超时（单次最大 600000 ms） |
| `webFetchTimeout` | 30000 ms | Web 抓取超时 |

注：`bash` 工具参数中 `dangerouslyDisableSandbox: true` 可绕过命令拦截（需用户授权才可执行）。

## 五、Plan 模式（只读）

- Plan 模式下，`ToolRegistry.getReadonlyDefinitions()` 只暴露只读工具：`read_file`、`list_directory`、`glob`、`grep` + MCP 工具 + plan 工具；**隐藏所有写文件、Shell、Web 类工具**。
- 模型在 Plan 模式调用被禁工具时，直接返回"plan mode 不可用"错误，提示 `/exit-plan` 解锁。

## 六、执行结果后处理

- 输出超过 200,000 字符自动截断并标记 `truncated`。
- 中断（AbortSignal）时返回 `interrupted` 结果。
- 文件工具受沙箱路径校验，越界访问返回 `Access denied`。

## 八、宿主注入工具的执行机制

### 1. 为什么需要"宿主注入"

内置工具（`packages/tool`）是**自包含**的：执行逻辑只依赖参数与 `ToolContext`。而 memory / plan 五件套的执行**依赖宿主的运行时状态**（记忆存储、计划引擎、会话路由），因此以"工厂函数 + 宿主回调注入"形式定义在 `packages/core/src/tool-factories.ts`：

| 工具 | 依赖的宿主能力 | 注入回调 |
|------|----------------|----------|
| `read_memory` | 记忆存储位置 | `getStore(context)` |
| `write_memory` | 记忆存储位置、会话 ID（写入 `sourceSessionId` 溯源） | `getStore(context)` + `getSessionId(context)` |
| `submit_plan` | 是否处于 Plan 模式、计划引擎、前端推送 | `isPlanModeActive(context)` + `getPlanEngine(context)` + `publishPlan(context)` |
| `get_plan` | 当前计划状态 | `getPlanEngine(context).getPlan()` |
| `update_plan_step` | 当前计划状态 | `getPlanEngine(context).updateStep(...)` |

设计动机：CLI 与 Web 两种宿主的 store / plan engine / 会话路由实现不同，但工具描述与 Schema 必须单一来源，避免双份拷贝漂移。

### 2. 注册时机与宿主差异

- **CLI**（单会话）：memory 启用且 store 初始化成功才注册 memory 工具；plan 工具始终注册，注入的是进程级单例 `planModeState` / `planEngine`。
- **Web**（多任务并行）：同样按 memory 配置注册；但 plan 工具的回调按 `context.sessionId` 从 `conversations` Map 路由到**每个任务独立**的 `planModeActive` / `planEngine`。

### 3. 执行链路（与内置工具完全一致，无特判）

```
模型发起 tool_call
  └─ AgentLoop
      ├─ ① isToolBlocked 检查（Plan 模式只读集合含 read_memory/get_plan/submit_plan/ask_user）
      ├─ ② requestPermission（宿主实现：allow 放行；ask 模式仅 requiresPermission/isDangerous 询问，
      │        write_memory 需询问，plan 工具与 read_memory 免询问）
      └─ ③ executeTool → ToolExecutor.execute 统一流程
             lookup → validateParams → sandbox → execute()
             └─ 执行瞬间回调宿主闭包（getStore / getPlanEngine / publishPlan ...）
                → postProcess
```

### 4. 与内置工具的差异总结

| 维度 | 内置工具 | 宿主注入工具 |
|------|----------|--------------|
| 数据来源 | 参数 + 文件系统 | 参数 + 宿主闭包中的运行时状态 |
| 注册 | `registerBuiltinTools()` 一次全注册 | 按条件动态注册（如 memory 未启用则无 memory 工具） |
| 权限 / 沙箱 | 走同一套 PermissionManager / Sandbox | 完全相同（memory/plan 工具无路径/命令参数，不触发沙箱） |
| 子 Agent | 按 `canBeUsedInSubAgent` + `allowedTools` 过滤 | 同样受过滤（CLI 的 `spawn_sub_agent` 为 CLI 独有） |
